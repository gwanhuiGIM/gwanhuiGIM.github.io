한눈에 보기

인공지능 코딩 도구에 작업을 통째로 일임하지 않고, 어디까지 맡기고 어디서 사람이 직접 판단할지 경계를 나누어 협업 환경을 설계하고 운영해 온 기록입니다. 이 환경은 사람이 최종 결정할 승인 항목, 위험 행동을 거르고 맥락을 안내하는 가드레일, 특정 시점마다 자동으로 도는 훅(hook), 반복 작업을 표준화한 명령어와 스킬로 이루어져 있습니다. 규칙과 요구는 제가 정하고 설계·검토했으며, 스크립트와 지침 문서의 본문은 대부분 에이전트가 작성했습니다. 여러 프로젝트와 도구를 다루며 겪은 실수와 비효율을 바탕으로 규칙을 다듬고 자동화 장치를 덧붙여 왔습니다.

답변이 만들어지는 흐름

한 번의 요청이 답변으로 돌아오기까지 거치는 단계입니다. 단계마다 어떤 장치가 작동하는지 표시했고, 누르면 아래 설명으로 이동합니다.

  1. ①세션 시작

    지침과 이전 상태를 읽고 시작합니다

    • 전역·작업공간 지침
    • 상태 문서 주입·규칙 대조 훅
    • 이전 세션 인계

  2. ②요청 해석·계획

    물을 것만 묻고 계획을 세웁니다

    • 승인이 필요한 세 가지만 질문
    • 반복 절차는 명령어로

  3. ③작업 중

    되돌리기 어려운 실행은 직전에 막고, 검토는 작성자와 분리합니다

    • 실행 직전 차단·경고
    • 도구 실행 전후 훅
    • 서브에이전트·다른 모델 검토

  4. ④답변 마무리

    근거와 남은 결정을 드러내고 끝냅니다

    • 확신도·가정·확인 요청
    • 상태 갱신·감사 제안 확인 훅

  5. ⑤피드백

    실패와 지적을 규칙으로 되돌립니다

    • 규칙 한 줄 → 차단·명령어·지침
    • 상태 문서·인계로 다음 세션에

⑤ 피드백은 다시 ① 세션 시작의 지침과 상태로 들어갑니다 ↺ · 세션 밖에서 사람이 없을 때 도는 것은 곁들인 자동화.

단계별 장치

어떻게 여기까지 왔나①⑤↑ 흐름

에이전트를 매일 쓰면서 로보틱스 개발 환경의 기존 라이브러리와 충돌하는 패키지를 임의로 설치하거나 제대로 검증하지 않고 완료했다고 보고하는 등 크고 작은 문제를 겪었습니다. 대화창에서 구두로 주의를 주어도 세션(대화)이 바뀌면 같은 실수가 반복되었습니다.

이를 막고자 실패를 겪을 때마다 원인을 분석해 규칙 한 줄로 정리하고 문서화했습니다. 하지만 텍스트 규칙만으로는 작업 경로 변경처럼 즉각적인 통제가 필요한 행동을 온전히 막지 못했습니다. 이에 판단이 필요 없는 확정적 위험은 실행 직전에 가로채는 기계적 자동 장치로 승격시켰습니다.

이후 자주 쓰이는 복잡한 절차는 정형화된 명령어로 묶어 작업의 일관성을 높였습니다. 에이전트가 사람에게 질문하는 방식 또한 처음에는 질문 개수를 제한했다가 묻지 못한 가정을 실행해 되돌리는 일이 생겼고, 제한을 풀자 사소한 것까지 과도하게 물어 피로가 누적되었습니다. 수차례 조정을 거쳐 반드시 사람의 승인이 필요한 항목만 명확히 추려 묻도록 기준을 정립했습니다.

  1. 작업 일임
  2. 충돌·보고 오류 발생
  3. 규칙 문서화
  4. 규칙 위반 재발
  5. 실행 전 자동 차단
  6. 반복 절차의 명령어화
  7. 사용자 승인 기준 정립

사용자 승인 항목②④↑ 흐름

  • 겪은 불편: 에이전트의 확인 요청 횟수를 1~2개로 제한했을 때는 에이전트가 묻지 못한 가정을 임의로 실행했다가 작업을 통째로 되돌려야 했습니다. 반대로 상한을 없애자 사소한 구현 사항까지 일일이 물어와 사용자에게 과도한 검토 부담이 생겼습니다.
  • 만든 장치: 에이전트가 사람에게 묻는 지점을 세 가지로 엄격히 한정했습니다. ① 해석이 갈려 결과가 크게 달라지는 모호함, ② 기존 자료로 메울 수 없는 필수 결정, ③ 되돌리기 어렵거나 외부로 나가는 행동입니다. 질문할 때는 항목마다 추천안과 근거를 함께 제시해 사용자가 가부를 한 번에 판단할 수 있게 했고, 답하지 않은 항목은 미승인으로 처리하게 했습니다. 또한 실제 로봇 모션 실행과 코드 원격 반영(push)은 사람이 직접 하고, 원격 서버 접속과 전역 작업 지침 수정은 사람의 승인을 받은 뒤에만 하도록 정했습니다(지침 수정은 바뀌는 조건을 먼저 요약해 보여 줌). 응답 끝에는 확인된 사실과 에이전트가 자체적으로 채워 넣은 가정을 명시하도록 의무화했습니다.
  • 기대효과·체감: 사소한 질문에 쏟는 피로를 줄이면서, 결과가 크게 갈리거나 되돌리기 어려운 지점에서는 사람이 먼저 판단하도록 하는 것이 목적입니다.

가드레일 장치③↑ 흐름

  • 겪은 불편: 실수를 막으려고 무조건 "하지 마라" 식의 절대적인 금지 지침(방호벽)을 세우면, 다음 세션의 에이전트가 맥락 없이 그 금지를 과하게 적용하거나 맹목적으로 지키다가, 오히려 잘못된 방향으로 작업을 해 버리는 경우가 있었습니다.
  • 만든 장치: '벽이 아니라 가드레일'이라는 원칙을 세웠습니다. 보안 자격증명, 파일 임의 삭제, 실제 로봇 모션, 코드 push처럼 되돌리기 어려운 위험에만 절대 차단을 적용했습니다. 그 외의 작업 지침은 일방적인 금지 대신 규칙을 만든 계기와 적용 범위, 막혔을 때의 대처 방안을 함께 기술하고, 기본 경로를 벗어날 때는 응답에 그 이유를 밝히도록 판단 여지를 주었습니다. 또한 정상적인 작업을 방해할 정도로 지나치게 가로막던 장치는 차단에서 경고로 완화하거나 감지 조건을 실제 명령 위치로 좁혀 조율했습니다.
  • 기대효과·체감: 네 가지 장치 모두 매일의 작업에 함께 쓰이지만, 그중 체감이 가장 컸던 장치입니다. 금지만 적힌 지침 때문에 잘못된 작업을 해 버리던 일이, 가드레일로 바꾸거나 에이전트가 먼저 묻고 맥락을 알려 주게 하면서 작업 방향을 다듬을 수 있게 되었다고 느꼈습니다(측정한 효과는 아닙니다).
  1. 맹목적 금지 지침
  2. 과잉 거부·오작동 발생
  3. 절대 차단(위험 행동)과 유연한 가드레일(맥락·대처 제시) 분리
  4. 작업 방향 안정 유도

훅 (Hook)①③④↑ 흐름

훅(hook)은 에이전트가 도구를 실행하기 전후나 세션이 시작되고 끝날 때 사람이 개입하지 않아도 백그라운드에서 자동으로 도는 스크립트 장치입니다. 안내 메시지가 늦게 도착해 위반이 먼저 실행되던 항목은 실행 전 차단으로 올리고, 정상 작업을 방해하던 것은 경고나 좁은 조건으로 완화하며 실효성을 높였습니다.

  • 세션 시작 시: 작업 공간의 현재 상태 문서가 없으면 기본 서식을 생성하고, 기존 문서가 있으면 그 내용을 새 세션에 주입해 이전 작업 흐름을 기억하도록 돕습니다. 전역 규칙 문서와 실제 차단 목록이 일치하는지도 대조합니다.
  • 실행 전 (도구 호출 직전): 임의의 작업 경로 변경(cd), 실제 로봇 모션, 코드 원격 반영(push) 등 위험하거나 반복되던 실수 명령을 실행 직전에 가로채 차단합니다. 다른 세션에 작업을 맡긴 상위 세션이 직접 파일을 수정하려 할 때도 경고를 띄웁니다.
  • 실행 후 (도구 호출 직후): 상태 문서의 크기가 지나치게 커지면 알림을 보내고, 문서가 수정된 뒤에는 독립 검토를 제안하라고 상기시키며 검토 결과를 받으면 판정 절차를 에이전트에 전달합니다.
  • 응답 종료 시: 코드 커밋 후 작업 상태 문서를 갱신하지 않고 끝내려 하거나 감사(독립 검토) 제안이 빠진 턴을 감지해 응답 종료를 한 번 막고 확인하게 합니다. 사용자 프롬프트 기록도 정리해 저장합니다.
  1. 세션 시작(상태 주입·규칙 대조)
  2. 실행 전(위험 명령 사전 차단)
  3. 실행 후(상태 크기 알림·검토 절차 주입)
  4. 응답 종료(상태 갱신 확인·기록 저장)

슬래시 커맨드·스킬②③↑ 흐름

슬래시 커맨드(/)는 반복되는 복잡한 절차를 단축 명령어로 표준화한 것이고, 스킬(skill)은 에이전트에게 특정 역할이나 작업 규칙을 모아 제공하는 지침 모듈입니다. 서브에이전트(subagent)는 독립 검토 등 특정 역할에 맞게 도구와 권한을 분리해 호출하는 보조 에이전트를 뜻합니다.

  • /debug: 원인을 모른 채 짐작으로 코드를 고치는 땜질 수정을 막기 위해, 재현(수정 금지) → 실제 명령을 통한 관측 → 가설 수립 및 배제 실험 → 최소 수정 및 빌드 확인 → 규칙 한 줄 반영으로 이어지는 디버깅 절차를 밟게 합니다.
  • /dump: 대화 도중 흘리듯 나온 정보가 휘발되는 것을 막기 위해, 메모를 제약 사항, 결정 사항, 해결할 질문 등으로 분류해 적절한 파일로 분배하고 모순이 있으면 사용자에게 되묻습니다.
  • /quiz: 에이전트가 작성한 코드를 개발자가 완전히 이해하지 못해 블랙박스가 되는 부채를 방지하고자, 최근 코드 변경점을 바탕으로 에이전트가 개발자에게 역으로 질문을 내어 이해도를 시험하도록 구성했습니다.
  • /cover-letter: 지원 서류 작성 절차가 한데 뭉쳐 에이전트에게 흐름 작성을 맡겼다가 사용자 의도와 어긋나던 문제를 줄이고자 단계를 분리했습니다. 소재 선정과 흐름 선택 등 핵심 판단은 사용자 승인 단계로 묶고, 본문 작성, 사실 검증, 문체 보존 검사를 단계별로 거치도록 했습니다.
  • write-readme: 단순 코드 나열이나 근거 없는 과장 표현을 줄이고, 표준 서식 흐름에 따라 실제 동작 중심의 검증된 내용으로 프로젝트 소개 문서를 작성하도록 유도하는 지침입니다.
  • codex-delegate: 다른 에이전트에 교차 검토를 맡길 때 발생하는 기술적 오류를 방지하고, 외부 검토 의견을 무비판적으로 수용하지 않도록 수용·기각·보류 판정표를 작성하게 하는 지침입니다.
  • herdr 운영: 단일 대화창에 여러 작업을 몰아넣어 문맥이 과부하되는 문제를 줄이고자, 작업을 독립된 터미널 창의 작업자 세션으로 나누어 띄우고 중심 세션은 지시와 판정만 전담하도록 분리했습니다. 시스템 부하를 고려해 동시 실행 수는 기본 2개씩으로 조율했습니다.

단일 모델에 의존하지 않고 작업 성격에 맞추어 모델과 연산 강도(effort)를 유동적으로 배분했습니다. 전체 계획 수립과 최종 판정은 메인 에이전트가 맡고, 결과물의 독립 검토는 도구를 제한한 서브에이전트에게, 교차 검증은 다른 회사 모델에게 맡겼으며, 외부 독자용 본문 서술을 맡긴 모델은 중간 강도로 지정했습니다. 연산 강도가 무조건 높다고 좋은 결과가 나오는 것은 아니라는 경험을 바탕으로, 작업 단위에 맞추어 도구와 모델을 조합했습니다.

세션 인계①⑤↑ 흐름

  • 겪은 불편: 에이전트는 세션이 새로 시작되면 이전 대화 맥락과 진행 상태를 기억하지 못합니다. 그렇다고 한 세션을 길게 유지하면 요청마다 앞선 대화를 다시 보내 사용량이 커지고, 대화가 쌓여 답변 품질도 떨어진다고 판단했습니다.
  • 만든 장치: 세션이 끊겨도 맥락을 이어받을 수 있도록 현재 작업 상태 문서를 단일 출처로 두고 덮어쓰며 관리했습니다. 문서가 과도하게 커지지 않도록 글자 수 상한을 두었습니다. 병렬 작업 시에는 주제별 인계 메모 문서를 두어 작업이 끝나면 중심 상태 문서에 반영한 뒤 정리하도록 했습니다. 다른 세션에 작업을 넘길 때는 대화에만 있던 맥락을 인계 파일로 옮기게 하고, 주제가 바뀌면 새 세션을 열도록 권하게 했습니다. 인계 문서가 새 세션의 입력창으로 넘어왔을 때 에이전트가 이를 사용자가 직접 보낸 새 지시로 오인하지 않도록, 출처가 확인된 내용만 사용자 결정으로 보고 나머지는 착수 전 확인 질문을 거치도록 규칙을 보강했습니다.
  • 기대효과·체감: 긴 대화의 사용량 부담과 문맥 혼선을 줄이면서, 세션을 바꿔도 진행 상황과 결정 사항이 이어지도록 하는 것이 목적입니다. 인계문 출처 규칙은 실제 혼동을 겪은 뒤 최근에 더한 것이라 효과는 아직 지켜보는 중입니다.
  1. 작업 진행 및 상태 기록
  2. 주제 전환 시 인계 문서 작성
  3. 새 세션 시작
  4. 인계 문서 주입 및 착수 전 확인 질문
  5. 작업 연속 수행

곁들인 자동화

아래 중 세 도구(subdisplay·usage-indicator·tok_refresh)는 공개 저장소 agent-sidekick-tools에 코드가 있습니다.

  • subdisplay: 태블릿을 보조 화면으로 연결하여 에이전트 상태, 점검 목록, 시스템 리소스 현황을 로컬 문서 기반으로 실시간 공유하는 도구입니다.
  • usage-indicator: 여러 에이전트 CLI의 사용량과 갱신 잔여 시간을 상단 패널에 상시 표시하고 파일로 공유해 중복 조회를 방지하는 모니터링 도구입니다.
  • tok_refresh: 5시간 단위 사용량 제한은 첫 요청 시점에 따라 갱신 시각이 매일 달라집니다. 클라우드 예약 작업이 정해진 시각마다 짧은 요청을 보내 그 시각을 고정하고, 하루 사용량을 업무 시간에 맞춰 나눠 쓰게 하는 장치입니다.
  • 일일 브리핑: 여러 작업 공간의 변경 이력과 상태를 모아 요약하고 다른 모델로 교차 점검해 보고서를 생성하는 수동 실행 요약 절차입니다(교차 점검은 보조라, 실패한 날에는 점검 없이 생성).
  • 지원현황 점검: 지원 서류 폴더의 위치, 마감일, 상태 표기 불일치를 매일 밤 자동으로 점검해 정리하고 변경 사항이 있을 때만 알림을 주는 스크립트입니다.
  • 사실 보존 검사: 문체를 자연스럽게 다듬는 과정에서 수치, 코드 낱말, 인용구 등 핵심 사실이 왜곡되거나 누락되지 않았는지 전후 차이를 대조하는 검사 도구입니다.

배운 점·한계

협업 체계를 운영하면서 이미 잘못 진행된 작업을 되돌려 처음부터 다시 시작하는 비용을 치르기보다, 작업 착수 전에 방향과 범위를 명확히 정의하고 계획을 꼼꼼하게 수립·검증하는 것이 무엇보다 중요하다는 점을 배웠습니다. 최고 성능의 플래그십 모델이라도 모든 과정에 똑같이 쓰기보다 작업 성격과 단위에 맞추어 모델을 분배하고 연산 강도를 조절하는 유동적인 협업 감각을 익혔습니다. 실제로 이러한 장치들을 통해 개발과 문서 작업 전반에서 불필요한 시행착오를 줄이고 진행 시간을 아낄 수 있었습니다.

다만 자동 차단 장치는 위험한 명령의 실행을 막은 것이지, 실제 사고를 막았다는 뜻은 아닙니다. 차단 건수 중 일부는 규칙 검증을 위한 시험이거나 정상 입력을 막았던 오탐이 포함되어 있으며, 작업 효율과 안전 효과는 체감에 기반한 것으로 정밀하게 수치화하여 측정한 것은 아닙니다. 규칙을 한 번 정한다고 끝나는 것이 아니라, 작업 변화에 맞춰 가드레일과 승인 기준을 지속적으로 관찰하고 다듬어 나가는 과정이 필수적이었습니다.
