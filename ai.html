AI 협업의 기준과 원칙

모든 과정을 AI에 일임하지 않습니다. AI에게 진행 경과를 묻고 확인하되, 해석이 갈리거나 되돌리기 어려운 결정처럼 승인이 필요한 지점은 AI가 먼저 묻도록 규칙을 세웠습니다. 이런 ‘작업 가이드 엔지니어링’으로 협업 환경을 설계하고 운영해 왔습니다.

  • 규칙 경위 기록 126건: 불편과 실수를 겪을 때마다 원인을 짚어 한 줄 규칙으로 정리하고 그 배경을 쌓아 가며 개선해 왔음을 보여 줍니다.
  • 실행 단계 자동 차단 규칙 14개: 주의 문구에 머무르지 않고 되돌리기 어렵거나 반복되는 실수는 프로그램 실행 직전에 기계적으로 막는 안전망을 구축했습니다.
  • 설계·조정한 명령어·스킬 4개와 자동화 도구 6개: 반복되는 작업 병목과 비효율을 마주할 때마다 이를 표준 절차와 전용 도구로 구조화하고, 사람이 일일이 챙기던 반복 확인을 기계에 맡겨 두었음을 보여 줍니다.

일하는 방식: 통제와 위임의 경계

  1. 목표·범위 지정(사람)
  2. 계획 작성(AI)
  3. 다른 모델로 계획 검증(AI)
  4. 계획 승인(사람)
  5. 작업(AI, 필요하면 여러 세션으로)
  6. 작성자와 분리된 검증(AI)
  7. 지적 판정(AI)
  1. 판단이 필요한 것 → 사람에게 질문·승인(사람)
  1. 원본으로 확인된 오류 → 바로 복구(AI)
  1. 둘 다 반영
  2. 결정·진행 기록
  3. 다음 작업의 계획으로 ↺

인공지능 도구에 처음부터 끝까지 혼자 알아서 끝내도록 위임하지 않습니다. 문제의 목표와 지켜야 할 제약을 사람이 먼저 정의한 뒤 계획을 세우게 하고, 실제 작업에 착수하기 전에 사람이 계획의 타당성을 검토해 승인합니다. 사람이 진행 경과를 확인하는 데 그치지 않습니다. 해석이 갈려 결과가 크게 달라질 때·자료로 메울 수 없는 결정·되돌리기 어려운 행동처럼 판단이 필요한 지점에서는 AI가 사람에게 묻도록 규칙을 두어 승인 경계를 구분했습니다. 초안 작성과 코드 구현은 AI에게 맡기되, 결과물은 작성자가 아닌 별도의 검증 역할을 부여한 AI로 교차 점검합니다. 검증 지적 사항 중 판단이 필요한 것은 사람에게 물어 승인을 받고 확인된 오류는 AI가 바로 복구하며, 둘 다 반영과 기록을 거쳐 다음 작업의 계획으로 돌아가도록 흐름을 합류시켰습니다. 실제 로봇 동작·원격 서버 접속·공개 저장소 반영처럼 되돌리기 어렵거나 밖으로 나가는 행동과 계획·소재 선택은 사람이 직접 승인합니다.

모델·코딩 도구 활용

하나의 모델에 모든 작업을 몰아넣지 않고 작업 단위의 성격에 맞추어 모델과 연산 강도(effort)를 유동적으로 나누어 지정했습니다. 전체 계획 수립과 탐색, 최종 판정은 메인 코딩 에이전트가 맡고 구현된 결과물의 독립 검토는 도구를 제한한 서브 검토자에게 맡겼습니다. 산출물의 신뢰성을 높이려고 다른 회사 모델로 교차 검증을 거치되, 특정 모델에는 연산 강도 상한을 정해 두었습니다. 외부 독자를 위한 글은 본문 서술을 맡긴 모델의 연산 강도를 중간 수준으로 지정했습니다. 모델 성능이나 강도가 높다고 결과가 무조건 좋아지지는 않는다고 봤기 때문입니다. 다중 작업 세션을 띄울 때마다 목적에 맞는 모델을 직접 지정했고, 블라인드 독자 점검과 같은 가벼운 점검에는 경량 모델을 배치해 균형을 맞췄습니다.

업무를 구조화한 명령어와 스킬

1. /cover-letter (문서 작업 절차 단계화)

  1. 절차 몰림과 과위임
  2. 자료 선별 및 흐름 2안 선택
  3. 본문 분리 작성 및 사실 검증
  4. 윤문·사실 보존 검사 및 실측

문서 작성 절차가 한데 뭉쳐 흐름 작성을 AI에 맡겼다가 의도와 어긋나던 문제를 줄이고자 단계를 나눈 명령어입니다. 쓰는 AI에게는 문단 요약이나 예시 글(예시를 거의 그대로 옮겨 쓴 일이 있어 제외)을 넘기지 않고 근거 기록과 공고 정보·형식만 전달합니다. 제시된 흐름 두 안 중 지원자가 선택한 뒤 본문은 다른 AI가 작성하게 했습니다. 작성 후에는 쓴 쪽과 다른 회사 모델로 사실을 검증하고 문체를 다듬은 뒤 사실이 바뀌지 않았는지 기계적으로 검사합니다. 글자수는 본문을 쓴 AI가 적은 값 대신 스크립트로 실측해 확인합니다.

2. write-readme (소개 문서 작성 지침)

  1. 단순 코드 나열 문서
  2. 표준 서식 구조 적용
  3. 코드 기반 근거 대조
  4. 읽는 사람 중심 문서화

프로젝트 소개 문서가 단순한 코드 기능의 나열이나 근거 없는 보장 표현으로 흐려지는 불편을 줄이려고 설계한 지침입니다. 정해진 서식 흐름에 맞추어 맥락을 서술하게 하고 코드로 확인되지 않는 배경은 사용자에게 질문하며, 읽는 사람이 쉽게 이해할 수 있는 동작 중심으로 작성하도록 유도합니다.

3. codex-delegate (타 인공지능 위임 및 판정 지침)

  1. 외부 지적 무비판 수용
  2. 실행 제약 점검 및 전달
  3. 지적 사항별 근거 확인
  4. 수용·기각·보류 판정표

다른 AI 모델에 교차 검토를 맡겼을 때 생기는 도구 연동 오류를 방지하고 외부 지적을 무비판적으로 수용하던 현상을 막고자 만든 지침입니다. 프롬프트 전달 시 발생하는 기술적 오류를 막고 검토 의견마다 독립적인 근거가 있는지 확인해 수용, 기각, 보류로 나누어 판정하게 했습니다.

4. herdr 운영 조정 (터미널 다중 작업 환경 운영)

  1. 단일 창 문맥 과부하
  2. 보조 작업자 분할 배치
  3. 기본 동시 2개씩 실행
  4. 지휘 세션 취합 및 판정

한 대화에 여러 작업을 몰아넣어 문맥이 과부하되던 문제를 줄이고자 외부 다중 터미널 도구(herdr)에 맞추어 설계한 운영 규칙입니다. 보조 작업자들을 독립된 작업 창으로 나누어 띄웠고, 이후 다중 실행으로 생긴 시스템 부하를 고려해 동시 작업 수를 기본 2개씩으로 조정했습니다. 중심 작업 창은 작업 지시와 결과 판정만 전담하도록 역할을 분리했습니다.

반복 확인을 맡기는 자동화

1. subdisplay (보조 화면 작업 상태 공유)

  1. 작업 상태 분산 관찰 불편
  2. 마크다운 기반 데이터 취합
  3. 사설망 태블릿 보조 화면 실시간 표시

에이전트의 진행 상태, 체크리스트, PC 리소스 사용량, 공고 현황을 한눈에 파악하려고 에이전트 코딩으로 만들고 설계·검토한 보조 도구입니다. 로컬 마크다운 문서를 단일 출처로 삼아 동시 수정 충돌을 감지하며, 사설망 내 태블릿 화면으로 작업 흐름을 끊지 않고 상시 확인할 수 있게 했습니다.

2. usage-indicator (상단 패널 사용량 모니터링)

  1. 호출 뒤에야 한도 소진 인지
  2. 각 도구 조회 사용량 병렬 수집
  3. 상단 패널 표시 및 파일 공유

여러 인공지능 CLI를 번갈아 사용하면서 호출 후에야 한도 소진을 알게 되는 비효율을 막고자 에이전트 코딩으로 구현하고 설계·검토한 도구입니다. 각 도구에서 조회한 사용량과 리셋 잔여 시간을 상단 패널에 상시 표시합니다. 조회 결과는 캐시 파일로 공유해 다른 연동 스크립트가 중복 호출 없이 한도 상태를 참조하도록 구성했습니다.

3. tok_refresh (사용량 윈도우 스케줄링)

  1. 불규칙한 사용량 리셋 시각
  2. 정해진 시각 자동 신호 전송
  3. 5시간 윈도우 분할 및 결과 알림

5시간 사용량 제한 환경에서 첫 호출 시점에 따라 리셋 시각이 매일 흔들리는 것을 막으려고, 하루 사용량을 업무 시간에 맞춰 나눠 쓰도록 설계·운영하는 장치입니다. 클라우드 예약 작업으로 정해진 일과 시간마다 가벼운 요청을 보내 사용량 윈도우를 미리 열어 둡니다. 리셋 시각을 판정해 알림도 보내므로 작업 일정을 계획할 수 있습니다.

4. 일일 브리핑 (다중 작업 공간 종합 요약)

  1. 다중 작업 공간 관리 누락
  2. 작업 기록 및 변경점 수집
  3. 초안 생성 및 타 모델 대조

여러 프로젝트 작업 공간의 상태를 일일이 파악하기 어려운 부담을 덜려고 마련한 절차입니다. 하루 동안의 변경 이력과 상태를 모아 요약 문서를 생성하고 다른 AI 모델로 대조를 거치도록 했습니다(대조는 보조여서 실패한 날엔 대조 없이 생성). 토큰 소모 때문에 예약 실행을 끄고 필요할 때 수동으로 돌리며, 토큰을 쓰지 않는 매일 작업만 따로 떼어 밤마다 돌리고 있습니다.

5. 지원현황 점검 (지원 서류 폴더 상태 자동 정리)

  1. 다수 지원 폴더 관리 분산
  2. 매일 밤 상태 기계적 점검
  3. 폴더·상태 정리 및 변경 시 알림

여러 기업 지원 건의 문서와 진행 폴더가 늘어나면서 상태 관리가 흐트러지는 것을 막으려고 마련한 점검 스크립트입니다. 매일 밤 지원 폴더 위치·마감일·상태 표기가 어긋난 곳을 고치고, 마감 지난 건을 종료 폴더로 옮기며, 공고 요약 빈칸을 보고합니다. 실제로 바뀐 것이 있을 때만 알림을 보냅니다.

6. 사실 보존 검사 (문체 수정 후 사실 왜곡 검증)

  1. 자연스러운 문체 다듬기
  2. 수치·낱말·경계 단서 대조
  3. 차이 목록으로 알림

AI를 활용해 문장을 자연스럽게 다듬는 과정에서 핵심 사실이나 수치가 왜곡되는 문제를 막는 검증 도구입니다. 원문과 수정본 간의 수치, 영문/코드 낱말, 인용, 경계 단서(팀·본인·미검증 같은 낱말)가 그대로인지 기계적으로 비교해 차이를 목록으로 알려 줍니다.

지침 개선 루프와 조정 사례

  1. 작업 중 불편·실패 발견
  2. 규칙 한 줄 + 경위 기록
  1. 판단이 필요 없는 확정 사실
  2. 자동 차단·알림
  1. 반복되는 절차
  2. 명령어·스킬
  1. 그 밖의 원칙
  2. 지침 문서(전역·작업공간별)
  1. 발동 기록·감사로 점검
  2. 늦거나 빗나감 → 방식 전환(알림→차단)
    과하게 막음 → 조건 좁힘
  3. 다시 규칙 한 줄로 ↺

도구를 운영하며 겪은 실패와 불편은 일회성 주의로 끝내지 않고 개선 루프로 다듬었습니다. 원인을 분석해 도출한 규칙은 성격에 따라 프로그램 실행 직전의 자동 차단이나 알림, 표준 절차를 담은 명령어와 스킬, 작업 지침 문서로 역할을 나누어 배치했습니다. 이후 실제 발동 기록과 감사로 규칙의 실효성을 점검했습니다. 대응이 늦거나 빗나가는 규칙은 사후 알림에서 사전 차단으로 방식을 바꿨고, 정상적인 작업까지 과하게 막는 규칙은 문자열 속 문구까지 감지하던 차단 조건을 실제 명령 위치로 좁혔습니다.

사례 1: 작업 경로 변경 금지 규칙 (안내형에서 자동 차단형으로 전환)

에이전트가 작업 경로를 임의로 변경하면 이후 명령들이 엉뚱한 디렉터리에서 실행되는 문제가 있었습니다. 처음에는 경로 변경 명령어가 감지되면 주의 메시지를 보여 주도록 설정했으나, 안내 문구가 명령어 실행 뒤에 도착해 실제 위반이 그대로 일어났습니다. 발동 기록을 분석해 사후 안내 방식으로는 실수를 막을 수 없다고 판단했고, 명령어가 실행되기 전에 즉각 가로채는 기계적 차단 규칙으로 바꿨습니다. 차단형 전환 뒤에도 잘못된 경로 이동 시도는 계속 나왔지만 명령이 실행되기 전에 막혔습니다. 재발 방지가 아닌 피해 차단으로 작동했습니다.

사례 2: 확인 요청 규칙의 세 번 조정 (묻지 않아 생긴 사고와 너무 많이 물어 생긴 부담 사이)

에이전트가 사람에게 확인을 구하는 규칙은 시행착오를 거치며 세 차례 다듬었습니다. 초기에는 확인 요청 횟수를 1~2개로 제한했더니 에이전트가 묻지 못한 가정을 실행해 작업을 되돌리는 일이 생겼습니다. 그래서 확인 요청 상한을 없애고 답이 없으면 미승인으로 처리하게 바꾸었으나, 너무 많이 물어 사람에게 부담이 생겼습니다. 이후 질문마다 추천과 근거를 붙여 한 번에 승인할 수 있게 개선했습니다. 지금은 해석이 갈려 결과가 크게 달라지는 경우, 필수 결정이 누락된 경우, 되돌리기 어려운 행동인 경우의 세 가지 기준으로 질문 범위를 한정해 쓰고 있습니다.

사례 3: 다중 보조 작업자 동시 실행 수 조정

여러 작업 창을 띄워 보조 작업자들을 실행했을 때, 한꺼번에 7개의 작업을 동시에 실행했다가 연산 부하가 치솟는 병목을 겪었습니다. 동시에 몰린 요청 탓에 서비스 사용량 한도에도 일찍 도달했습니다. 그래서 동시에 실행할 수 있는 작업자 수를 기본 2개씩으로 나누어 앞 묶음이 끝난 뒤 다음 묶음으로 이어가도록 지침을 수정했습니다.

토큰·사용량을 아끼는 장치

  • 상주 지침 문서의 비대화: 매 대화마다 읽히는 기본 지침에서 특정 상황에만 필요한 세부 항목을 분리해 전용 스킬 파일로 옮기고 상주 지침을 축약했습니다.
  • 모든 세션에 서술 규칙 주입: 일반 개발 작업 세션에까지 긴 글쓰기 규칙이 포함되던 비효율을 줄이고자, 서술 규칙을 별도 파일로 떼어 문서 작성 세션에서만 선택적으로 읽도록 바꿨습니다.
  • 작업 상태 기록 파일의 비대화: 진행 상황을 공유하는 상태 문서가 과도하게 커지지 않도록 전체 글자 수와 항목별 글자 수 상한을 두고 주입 크기를 제한했습니다.
  • 매 프롬프트 감사 제안의 부담: 대화가 오갈 때마다 매번 감사하자는 안(약 8만 토큰 규모)은 운영하지 않고 기각했으며, 감사는 작업 중간 1회와 끝 1회로 정했습니다.
  • 다중 모델 연동 시 과도한 로그 유입: 다른 모델에 검토를 위임할 때 긴 터미널 전체 실행 로그가 대화 맥락에 다시 들어오지 않도록, 최종 결과 메시지만 파일로 전달받도록 구성했습니다.
  • 매일 자동 실행의 토큰 소모: 매일 자동 실행되던 상태 요약(브리핑)이 토큰을 많이 써 예약 실행을 끄고 필요할 때만 돌리며 토큰을 쓰지 않는 매일 작업만 떼어 계속 돌렸습니다.
  • 메인 대화의 도구 출력 누적: 메인 대화가 직접 실행까지 맡아 도구 출력이 약 24만 자 쌓인 뒤, 메인은 판정만 하고 실행은 작업 세션에 넘기도록 바꿨습니다.
  • 동시 작업 세션의 사용량 집중: 사용량의 약 83%가 여러 작업 세션을 동시에 띄운 구간에서 나와, 작업 세션은 기본 동시 2개씩만 띄우도록 바꿨습니다.
  • 긴 대화의 반복 전송: 긴 대화는 요청마다 앞 대화를 다시 보내므로, 주제가 바뀌면 새 대화를 열도록 권하게 했습니다.
  • 흔들리는 사용량 리셋 시각: 5시간 사용량 윈도우가 첫 요청 시점에 열려 리셋 시각이 흔들려, 정해진 시각에 윈도우를 여는 예약 작업(앞의 tok_refresh)을 두었습니다.

배운 점

이러한 협업 체계를 구축하고 운영하면서 실제 개발과 문서 작업 전반에서 소요 시간을 줄일 수 있었습니다. 특히 이미 잘못 진행된 작업을 되돌려 처음부터 다시 시작하는 것보다, 착수 전에 방향과 작업 범위를 분명히 정하고 계획을 꼼꼼하게 세우는 일이 무엇보다 중요하다는 점을 체감했습니다. 최고 성능의 플래그십 모델이라도 모든 과정에 똑같이 쓰기보다, 작업의 성격과 단위에 맞추어 모델을 분배하고 연산 강도(effort)를 유동적으로 조절해 활용하는 균형 감각도 배웠습니다. 다만 자동 차단은 실행을 막은 것이지 실제 사고를 막았다는 뜻은 아니며, 일부는 규칙 시험이나 정상 입력을 막은 오탐이었습니다.
