한눈에 보기

인공지능 코딩 도구에 작업을 통째로 일임하지 않고, 어디까지 맡기고 어디서 사람이 직접 판단할지 경계를 나누어 협업 환경을 설계하고 운영해 온 기록입니다.

  • 구성사람이 최종 결정할 승인 항목 · 위험 행동을 거르고 맥락을 안내하는 가드레일 · 특정 시점마다 자동으로 도는 훅(hook) · 반복 작업을 표준화한 명령어와 스킬
  • 역할 분담규칙과 요구는 제가 정하고 설계·검토 · 스크립트와 지침 문서의 본문은 대부분 에이전트가 작성
  • 다듬어 온 방식여러 프로젝트와 도구를 다루며 겪은 실수와 비효율을 바탕으로 규칙을 다듬음 · 매번 직접 지시하던 일은 훅과 가드레일로, 반복되던 사용량 확인과 점검 일부는 별도 유틸리티로 자동화(일부 코드: agent-sidekick-tools)
부트캠프 팀 프로젝트에서 에이전트를 쓰며 개발한 방식

부트캠프 로봇 팀 프로젝트에서는 팀원마다 맡은 개발에 AI 코딩 에이전트를 활용했습니다.

  • 저의 활용 범위저는 에이전트를 코드 로직 구성과 개발 환경 구성 보조, 구조 제안까지만 씀
  • 직접 하려 한 일작업 흐름(상태·우선순위)을 짜는 일 · 문제의 원인을 규명하는 일
  • 겪은 일다만 핵심 원인을 실기나 디버깅으로 짚지 못하고 있으면, 에이전트가 추정한 원인을 고치는 쪽으로 잘못 매달리는 일이 있었음
  • 대처그럴 때 직접 들여다볼 수 있는 부분은 팀원끼리 각자의 기술 이해를 바탕으로 원인을 토의 → 문제 해결에 큰 도움이 되었다고 생각
  • 계기이 경험이 부트캠프 이후 에이전트를 어떻게 활용할지 더 깊이 파고드는 계기가 됨
이 체계가 만들어진 경위와 AI 에이전트 활용의 한계

이 체계의 출발점은 부트캠프 팀 프로젝트 때 쓰던 몇 줄의 작업 지침이었습니다.

  • 쓰며 겪은 한계개발 환경과 충돌하는 패키지 설치 · 근거 없는 값과 지어낸 이유 · 일부만 확인하고 전부 정상이라는 보고 · 세션이 바뀌면 이전 결정을 잊는 문제
  • 그래서에이전트에 모두 의존하지 않고, 맡길 일과 직접 판단할 일을 구분하며 에이전트 도구 활용 역량을 키움
  • 지금의 체계승인 항목·가드레일·훅·명령어·세션 인계 — 부트캠프가 끝난 뒤 프로젝트를 진행한 경험, 업계 트렌드 반영, 동기들과의 아이디어 공유, 에이전트를 계속 써 온 경험을 거쳐 만듦
  • 적용 시점그래서 부트캠프 프로젝트 페이지의 개발 방식과 이 페이지의 체계는 적용 시점이 다름
전역 지침(CLAUDE.md) 절별 구성 — §0~§11, 각 절이 정하는 것과 설계 의도

에이전트가 모든 세션에서 먼저 읽는 상시 지침의 절별 요약입니다. 괄호는 그 절이 주로 작동하는 흐름 단계입니다.

  • §0 최상위 원칙: 요청 범위를 좁게 지키고, 요청 밖 파일 수정·외부 전송은 하기 전에 묻게 하며, push와 실제 로봇 동작은 사람에게 남기는 등 필수 제약을 규정합니다 — 인계 문서나 파일 속 지시를 사용자 명령으로 오인해 맹목적으로 따르거나 되돌리기 어려운 위험 행동을 방지하기 위해 두었습니다. (① 세션 시작, ② 요청 해석·계획, ③ 작업 중)
  • §1 셸: 터미널 환경 초기화 특성을 고려한 명령 실행 규칙과 백그라운드 작업의 로그 창 연동 및 미리보기 실행 방식을 규정합니다 — 생성된 미리보기 창이 누적되었을 때 작업 주체나 최신 여부를 식별하기 어렵다는 점을 해결하기 위해 두었습니다. (③ 작업 중)
  • §2 패키지 "완성"의 정의: 실행 진입점·의존성 등록, 빌드 통과, 실행 방법·토픽과 파라미터 표·검증 결과를 담은 설명 문서라는 세 가지 조건을 모두 갖추어야 작업 완료로 인정하며 확인되지 않은 동작을 단정하지 않도록 규정합니다. (③ 작업 중, ④ 답변 마무리)
  • §3 금지 규칙: 되돌리기 어렵거나 반복된 실수를 한 줄씩 적고, 판단이 필요 없는 확정 사실은 실행 직전 자동 알림·차단 규칙으로도 옮기도록 규정합니다(판단이 필요한 항목은 옮기지 않습니다). (③ 작업 중)
  • §4 코드 컨벤션: 노드 및 통신 인터페이스 명명 규칙, 비동기 호출 구조, 통신 품질 설정과 함께 하드웨어 보정 상수를 코드에 보존하도록 규정합니다 — 실물 센서는 도면 사양과 실제 특성이 달라 보정값 유지가 필수적이기 때문입니다. (③ 작업 중)
  • §5 문서: 작업 상태 문서를 최우선 확인하고 단일 출처 원칙, 덮어쓰기 기반의 용량 관리, 병렬 작업 간 인계 파일 분리와 시각 단위 기록을 규정합니다 — 사본 생성으로 인한 버전 혼선과 분실을 방지하고, 병렬 세션 간 간섭이나 같은 날 진행된 작업 이력이 뭉개지는 것을 막기 위해 두었습니다. (① 세션 시작, ③ 작업 중, ④ 답변 마무리)
  • §6 응답 계약: 실질적 답변마다 확신도, 에이전트가 자체 반영한 가정, 사용자 확인 요청을 명시하고 세 가지 경우(해석이 갈리는 모호함, 자료로 메울 수 없는 누락, 되돌리기 어렵거나 밖으로 나가는 행동)에만 승인을 묻도록 제한합니다. 새 규칙은 금지만 적지 않고 이유·적용 범위·막힐 때의 대처를 함께 쓰게 합니다 — 맥락 없는 금지는 다음 세션에서 과잉 적용되거나 맹목적으로 지켜지기 때문입니다. (② 요청 해석·계획, ④ 답변 마무리, ⑤ 피드백)
    • §6-1 "검증됨"의 정의: 동일한 작업 턴에서 실제 도구 실행 출력으로 직접 확인한 범위에만 '검증됨' 표기를 허용하고, 미확인 내역은 엄격히 구분하도록 규정합니다 — 잘못된 검증 표기가 사실 확인에 드는 비용을 사용자의 시간으로 떠넘기기 때문입니다. (③ 작업 중, ④ 답변 마무리)
    • §6-2 응답 언어 · 용어: 기본 설명과 요약은 한국어로 작성하되 현장에서 통용되는 실무 전문 용어는 억지로 번역하지 않고 영어 원어를 유지하도록 규정합니다. (④ 답변 마무리)
    • §6-3 범위·계획 승인 형식: 작업 계획이나 범위를 승인받을 때 사용자 원문 인용 대조표를 작성하여 자체 추가 항목과 누락 항목을 명시하도록 규정합니다 — 지시를 지나치게 좁게 해석했거나 범위를 임의로 부풀린 지점을 승인 시점에 명확히 드러내기 위해 두었습니다. (② 요청 해석·계획)
  • §7 실패했을 때: 원인 규명 전 임의 수정을 금지하고 단계적 진단을 거치며, 근본 원인은 재발 방지 규칙으로 승격하고 물리값 오류는 하드웨어 요인부터 점검하도록 규정합니다 — 섣부른 수치 조정은 증상만 가릴 뿐이므로 동일 실수를 구조적으로 방지하기 위해 두었습니다. (③ 작업 중, ⑤ 피드백)
  • §8 코드를 쓴 뒤: 변경 이유와 검토 지점을 요약 보고하고, 노드·모션·좌표 변환 코드는 커밋 전 독립 교차 리뷰를 거치며 실기 검증 지식의 문서화를 제안하도록 규정합니다 — 코드를 작성한 주체는 자기 논리의 모순을 스스로 보기 어렵고, 현장에서 확인한 지식이 후속 작업으로 이어지지 못하고 유실되는 것을 막기 위함입니다. (③ 작업 중, ④ 답변 마무리)
  • §9 세션 관리: 작업 단위를 마칠 때 확인할 체크리스트(조건에 맞으면 교차 감사 제안, 상태가 바뀌었을 때만 상태 문서 갱신, 보류 항목 설명, 남은 일에 따라 세션 종료 제안)를 규정합니다 — 오류가 다른 영역으로 번지는 것을 조기에 차단하고, 긴 세션은 요청마다 앞 대화를 다시 보내 사용량이 커지므로 주제가 바뀌면 새 세션을 권하기 위해 두었습니다. (② 요청 해석·계획, ③ 작업 중, ④ 답변 마무리)
  • §10 Codex 병행: 다른 AI 도구를 활용한 구현 위임 및 교차 검증의 제안 시점과 실행 기준을 규정합니다 — 작업을 마친 뒤의 감사는 세부 구현에 매몰되어 계획 자체의 잘못을 놓치기 쉬우므로 착수 전 단계부터 검증하기 위해 두었습니다. (② 요청 해석·계획, ③ 작업 중, ④ 답변 마무리)
  • §11 검증 루프 우선: 지시 프롬프트를 다듬기 전에 독립 테스트와 자가 검증 환경부터 구축하고, 검증 로직 자체가 실패를 정상 감지하는지 확인하도록 규정합니다 — 검증 코드 또한 구현자의 맹점을 공유하기 때문입니다. (② 요청 해석·계획, ③ 작업 중)

답변이 만들어지는 흐름

세션을 시작해 요청을 받고 답변을 내기까지 거치는 단계입니다. 단계마다 어떤 장치가 작동하는지 표시했고, 누르면 아래 설명으로 이동합니다.

  1. ①세션 시작

    지침과 이전 상태를 읽고 시작합니다

    • 전역·작업공간 지침
    • 상태 문서 주입·규칙 대조 훅
    • 이전 세션 인계

  2. ②요청 해석·계획

    물을 것만 묻고 계획을 세웁니다

    • 승인이 필요한 세 가지만 질문
    • 반복 절차는 명령어로
    • 계획 반대 심문

  3. ③작업 중

    되돌리기 어려운 실행은 직전에 막고, 검토는 작성자와 분리합니다

    • 실행 직전 차단·경고
    • 도구 실행 전후 훅
    • 서브에이전트·다른 모델 검토

  4. ④답변 마무리

    근거와 남은 결정을 드러내고 끝냅니다

    • 확신도·가정·확인 요청
    • 상태 갱신·감사 제안 확인 훅
    • 마무리 감사

  5. ⑤피드백

    실패와 지적을 규칙으로 되돌립니다

    • 규칙 한 줄 → 차단·명령어·지침
    • 상태 문서·인계로 다음 세션에

⑤ 피드백은 다시 ① 세션 시작의 지침과 상태로 들어갑니다 ↺ · 작업 세션 밖에서 도는 도구·절차는 곁들인 자동화.

단계별 장치

어떻게 여기까지 왔나①⑤↑ 흐름

에이전트를 매일 쓰면서 로보틱스 개발 환경의 기존 라이브러리와 충돌하는 패키지를 임의로 설치하거나 제대로 검증하지 않고 완료했다고 보고하는 등 크고 작은 문제를 겪었습니다. 대화창에서 구두로 주의를 주어도 세션(대화)이 바뀌면 같은 실수가 반복되었습니다.

이를 막고자 실패를 겪을 때마다 원인을 분석해 규칙 한 줄로 정리하고 문서화했습니다. 하지만 텍스트 규칙만으로는 작업 경로 변경처럼 즉각적인 통제가 필요한 행동을 온전히 막지 못했습니다. 이에 판단이 필요 없는 확정적 위험은 실행 직전에 가로채는 기계적 자동 장치로 승격시켰습니다.

이후 자주 쓰이는 복잡한 절차는 정형화된 명령어로 묶어 작업의 일관성을 높였습니다.

  • 질문 방식에이전트가 사람에게 질문하는 방식 또한 처음에는 질문 개수를 제한 → 묻지 못한 가정을 실행해 되돌리는 일이 생김 · 제한을 풀자 사소한 것까지 과도하게 물어 피로가 누적
  • 정립한 기준수차례 조정을 거쳐, 반드시 사람의 승인이 필요한 항목만 명확히 추려 묻도록
  1. 작업 일임
  2. 충돌·보고 오류 발생
  3. 규칙 문서화
  4. 규칙 위반 재발
  5. 실행 전 자동 차단
  6. 반복 절차의 명령어화
  7. 사용자 승인 기준 정립

## 7. 실패했을 때

## 6. 응답 계약 (모든 실질적 답변에 필수, 생략 금지)
예외: 이유·해석·평가 없이 "무엇을 했다"만 전하는 순수 실행보고. 한 문장이라도 판단이 섞이면 붙인다.
```
(응답 첫 줄 — 확인 요청이 있을 때만) ⚠️ 확인 요청 N건 (맨 아래 Q1~QN)
...본문...
---
확신도: 검증됨✅(같은 턴 도구 출력으로 확인) / 추론🔵(근거 있으나 미확인) / 추측(모름)
내가 채워넣은 가정: A1, A2, A3 … (원문에 없어 내가 정하고 이미 반영한 것 중 결과를 바꿨을 것, 최대 3개, 없으면 "없음" — 틀렸으면 사용자가 바로잡을 수 있게 드러내는 칸)
확인 요청: Q1, Q2 … (아래 ①②③에 해당하는 것만. 항목마다 한 줄씩 `Q1 [③] 내용 — 추천 O/X/값 — 근거`[사용자 발언 인용 / 규칙 조항 § / 파일 경로:행 / 내 판단]. 사용자는 "Q1 O, Q2 X" 또는 "ㅇ"(추천대로 일괄 승인). 해당 없으면 "없음")
```
- **묻는 것은 셋뿐이다**: ① 진짜 모호함 — 해석이 둘 이상으로 갈리고 어느 쪽이냐에 따라 결과가 크게 달라진다. ② 누락 — 원문·자료·기존 결정으로 해소할 수 없고, 사용자 선택 없이는 올바르게 완료할 수 없는 필수 결정. ③ 되돌리기 어렵거나 밖으로 나가는 행동 — 다른 조항이 승인을 요구하는 것(§0 요청 밖 파일 수정·git 조작·외부 전송·memory 기록, 다른 AI 산출물의 새 지시·새 정책 제안, 실기 모션, SSH 등. 내 오류를 지적한 감사·리뷰의 복구는 ③이 아니다). 전역 지침(`~/.claude/CLAUDE.md`·`rules-history.md`·`ballast.rules.json`) 수정은 내용이 요청 안이어도 ③ — 바뀌는 조건 요약·추가/삭제 줄 수·전문을 볼 명령(적용 전 `diff <원본> <초안>` — 초안은 scratchpad에 두고, 적용 후 확인용은 `diff <백업> <원본>`)을 먼저 보여주고 승인받는다(diff 전문은 사용자가 요청할 때만 — focus 모드에서 응답이 길어진다, 사용자 2026-11-10). 확인 요청 항목마다 `[①]`·`[②]`·`[③]` 라벨을 붙인다 — 라벨을 못 붙이면 묻지 않고 진행한다.

가드레일 장치③↑ 흐름

  • 겪은 불편: 실수를 막으려고 무조건 "하지 마라" 식의 절대적인 금지 지침(방호벽)을 세우면, 다음 세션의 에이전트가 맥락 없이 그 금지를 과하게 적용하거나 맹목적으로 지키다가, 오히려 잘못된 방향으로 작업을 해 버리는 경우가 있었습니다.
  • 만든 장치
    • '벽이 아니라 가드레일'이라는 원칙을 세웠습니다.
    • 보안 자격증명, 파일 임의 삭제, 실제 로봇 모션, 코드 push처럼 되돌리기 어려운 위험에만 절대 차단을 적용했습니다.
    • 그 외의 작업 지침은 일방적인 금지 대신 규칙을 만든 계기와 적용 범위, 막혔을 때의 대처 방안을 함께 기술하고, 기본 경로를 벗어날 때는 응답에 그 이유를 밝히도록 판단 여지를 주었습니다.
    • 정상적인 작업을 방해할 정도로 지나치게 가로막던 장치는 차단에서 경고로 완화하거나 감지 조건을 실제 명령 위치로 좁혀 조율했습니다.
  • 기대효과·체감: 네 가지 장치 모두 매일의 작업에 함께 쓰이지만, 그중 체감이 가장 컸던 장치입니다. 금지만 적힌 지침 때문에 잘못된 작업을 해 버리던 일이, 가드레일로 바꾸거나 에이전트가 먼저 묻고 맥락을 알려 주게 하면서 작업 방향을 다듬을 수 있게 되었다고 느꼈습니다(측정한 효과는 아닙니다).

  2. 과잉 거부·오작동 발생
  3. 절대 차단(위험 행동)과 유연한 가드레일(맥락·대처 제시) 분리
  4. 작업 방향 안정 유도

훅 (Hook)①③④↑ 흐름

훅(hook)은 에이전트가 도구를 실행하기 전후나 세션이 시작되고 끝날 때 사람이 개입하지 않아도 백그라운드에서 자동으로 도는 스크립트 장치입니다. 안내 메시지가 늦게 도착해 위반이 먼저 실행되던 항목은 실행 전 차단으로 올리고, 정상 작업을 방해하던 것은 경고나 좁은 조건으로 완화하며 실효성을 높였습니다.

  • 세션 시작 시: 작업 공간의 현재 상태 문서가 없으면 기본 서식을 생성하고, 기존 문서가 있으면 그 내용을 새 세션에 주입해 이전 작업 흐름을 기억하도록 돕습니다. 전역 규칙 문서와 실제 차단 목록이 일치하는지도 대조합니다.
  • 실행 전 (도구 호출 직전): 임의의 작업 경로 변경(cd), 실제 로봇 모션, 코드 원격 반영(push) 등 위험하거나 반복되던 실수 명령을 실행 직전에 가로채 차단합니다. 다른 세션에 작업을 맡긴 상위 세션이 직접 파일을 수정하려 할 때도 경고를 띄웁니다.
  • 실행 후 (도구 호출 직후): 상태 문서의 크기가 지나치게 커지면 알림을 보내고, 문서가 수정된 뒤에는 독립 검토를 제안하라고 상기시키며 검토 결과를 받으면 판정 절차를 에이전트에 전달합니다.
  • 응답 종료 시: 코드 커밋 후 작업 상태 문서를 갱신하지 않고 끝내려 하거나 감사(독립 검토) 제안이 빠진 턴을 감지해 응답 종료를 한 번 막고 확인하게 합니다. 사용자 프롬프트 기록도 정리해 저장합니다.
  1. 세션 시작(상태 주입·규칙 대조)
  2. 실행 전(위험 명령 사전 차단)
  3. 실행 후(상태 크기 알림·검토 절차 주입)
  4. 응답 종료(상태 갱신 확인·기록 저장)

슬래시 커맨드·스킬②③↑ 흐름

슬래시 커맨드(/)는 반복되는 복잡한 절차를 단축 명령어로 표준화한 것이고, 스킬(skill)은 에이전트에게 특정 역할이나 작업 규칙을 모아 제공하는 지침 모듈입니다. 서브에이전트(subagent)는 독립 검토 등 특정 역할에 맞게 도구와 권한을 분리해 호출하는 보조 에이전트를 뜻합니다.

  • /debug: 원인을 모른 채 짐작으로 코드를 고치는 땜질 수정을 막기 위해, 재현(수정 금지) → 실제 명령을 통한 관측 → 가설 수립 및 배제 실험 → 최소 수정 및 빌드 확인 → 규칙 한 줄 반영으로 이어지는 디버깅 절차를 밟게 합니다.
  • /dump: 대화 도중 흘리듯 나온 정보가 휘발되는 것을 막기 위해, 메모를 제약 사항, 결정 사항, 해결할 질문 등으로 분류해 적절한 파일로 분배하고 모순이 있으면 사용자에게 되묻습니다.
  • /quiz: 에이전트가 작성한 코드를 개발자가 완전히 이해하지 못해 블랙박스가 되는 부채를 방지하고자, 최근 코드 변경점을 바탕으로 에이전트가 개발자에게 역으로 질문을 내어 이해도를 시험하도록 구성했습니다.
  • /cover-letter: 지원 서류 작성 절차가 한데 뭉쳐 에이전트에게 흐름 작성을 맡겼다가 사용자 의도와 어긋나던 문제를 줄이고자 단계를 분리했습니다. 소재 선정과 흐름 선택 등 핵심 판단은 사용자 승인 단계로 묶고, 본문 작성, 사실 검증, 문체 보존 검사를 단계별로 거치도록 했습니다.
  • write-readme: 단순 코드 나열이나 근거 없는 과장 표현을 줄이고, 표준 서식 흐름에 따라 실제 동작 중심의 검증된 내용으로 프로젝트 소개 문서를 작성하도록 유도하는 지침입니다.
  • codex-delegate: 다른 에이전트에 교차 검토를 맡길 때 발생하는 기술적 오류를 방지하고, 외부 검토 의견을 무비판적으로 수용하지 않도록 수용·기각·보류 판정표를 작성하게 하는 지침입니다.
  • herdr 운영: 단일 대화창에 여러 작업을 몰아넣어 문맥이 과부하되는 문제를 줄이고자, 작업을 독립된 터미널 창의 작업자 세션으로 나누어 띄우고 중심 세션은 지시와 판정만 전담하도록 분리했습니다. 시스템 부하를 고려해 동시 실행 수는 기본 2개씩으로 조율했습니다.

단일 모델에 의존하지 않고 작업 성격에 맞추어 모델과 연산 강도(effort)를 유동적으로 배분했습니다.

  • 계획·판정전체 계획 수립과 최종 판정은 메인 에이전트
  • 독립 검토결과물의 독립 검토는 도구를 제한한 서브에이전트
  • 교차 검증다른 회사 모델
  • 본문 서술외부 독자용 본문 서술을 맡긴 모델은 중간 강도로 지정
  • 기준연산 강도가 무조건 높다고 좋은 결과가 나오는 것은 아니라는 경험을 바탕으로, 작업 단위에 맞추어 도구와 모델을 조합

독립 감사·검토②③④↑ 흐름

작성한 에이전트가 자기 결과를 스스로 채점하지 않도록, 작업을 보조하는 도구와 별개로 맥락을 분리한 감사·검토 역할을 두었습니다. 언제 부르고 결과를 어떻게 받을지도 규칙과 훅으로 엮었습니다.

검토자언제무엇을 보나
session-auditor사실을 기록한 작업의 마무리, 외부로 내보내기 전요청한 것과 실제로 한 일, 요청 밖의 일과 빠뜨린 일
devils-advocate계획 승인 직전계획이 현실에서 깨질 지점
cross-review·ros-verifier노드·모션·좌표 변환 코드 커밋 전, 구현을 끝냈다고 할 때구현 맥락을 모르는 눈으로 본 코드, ROS 2 변경
다른 회사 모델(Codex)계획 착수·코드 커밋·서류 완료 전산출물 교차 대조(읽기 전용)

훅·가드레일 연계

  • 문서를 고치거나 커밋한 턴에 감사 제안이 빠지면 훅이 응답을 한 번 막아 확인하게 하고, 감사를 부르면 결과를 받을 때의 판정 절차를 상기시켜 지적마다 원본과 대조해 수용·기각을 가리게 합니다.
  • 서브에이전트 검토자에는 편집 도구를 주지 않고 수정 금지를 역할 지침으로 둡니다(명령 실행 도구가 열려 있어 완전히 막지는 못합니다). AI 검토는 작업을 자동으로 멈추지 않는 권고입니다.

기대효과·체감: 감사·검토가 승인 없이 적용된 정책 수정이나 착수 전 계획의 공개 노출 위험을 찾은 일이 있었습니다. 모든 요청마다 감사하는 안은 비용이 커서 기각하고, 작업 중간 한 번과 끝에 감사하도록 조정했습니다. 효과를 측정한 것은 아닙니다.

  1. 계획·작업 수행
  2. 규칙·훅이 감사 시점 제시
  3. 분리된 검토자 실행
  4. 원본 대조 후 수용·기각
  5. 맞은 지적만 반영

세션 인계①⑤↑ 흐름

  • 겪은 불편: 에이전트는 세션이 새로 시작되면 이전 대화 맥락과 진행 상태를 기억하지 못합니다. 그렇다고 한 세션을 길게 유지하면 요청마다 앞선 대화를 다시 보내 사용량이 커지고, 대화가 쌓여 답변 품질도 떨어진다고 판단했습니다.
  • 만든 장치
    • 세션이 끊겨도 맥락을 이어받을 수 있도록 현재 작업 상태 문서를 단일 출처로 두고 덮어쓰며 관리했습니다.
    • 문서가 과도하게 커지지 않도록 글자 수 상한을 두었습니다.
    • 병렬 작업 시에는 주제별 인계 메모 문서를 두어 작업이 끝나면 중심 상태 문서에 반영한 뒤 정리하도록 했습니다.
    • 다른 세션에 작업을 넘길 때는 대화에만 있던 맥락을 인계 파일로 옮기게 하고, 주제가 바뀌면 새 세션을 열도록 권하게 했습니다.
    • 인계 문서가 새 세션의 입력창으로 넘어왔을 때 에이전트가 이를 사용자가 직접 보낸 새 지시로 오인하지 않도록, 출처가 확인된 내용만 사용자 결정으로 보고 나머지는 착수 전 확인 질문을 거치도록 규칙을 보강했습니다.
  • 기대효과·체감: 긴 대화의 사용량 부담과 문맥 혼선을 줄이면서, 세션을 바꿔도 진행 상황과 결정 사항이 이어지도록 하는 것이 목적입니다. 인계문 출처 규칙은 실제 혼동을 겪은 뒤 최근에 더한 것이라 효과는 아직 지켜보는 중입니다.
  1. 작업 진행 및 상태 기록
  2. 주제 전환 시 인계 문서 작성
  3. 새 세션 시작
  4. 인계 문서 주입 및 착수 전 확인 질문
  5. 작업 연속 수행

## 9. 세션 관리
**작업 단위(패키지 하나, 버그 하나) 종료 체크리스트** — 커밋·"완료" 보고 중 하나라도 하는 턴에 순서대로:
1. (노드·모션·좌표 변환 코드면) 커밋 전 `@cross-review` 대응 완료(§8), Codex 리뷰 제안(§10).
2. (문서·state.md·memory에 사실을 기록한 작업이거나, push 대기 커밋을 보고하기 전·외부 전송·여러 저장소 git 조작 직전이면) `session-auditor`와 Codex 교차검증(§10)을 함께 제안한다(동시에 돌리고 서로 결과를 넘기지 않는다 — 증거 부족 보류 지적의 재현 확인만 예외, `codex-delegate` §2). 넓은 작업은 범위 목록 승인 후 첫 영역이 끝났을 때도 한 번 — 끝에서만 잡으면 오류가 이미 번져 있다. **감사(auditor·Codex 등)가 이미 끝낸 작업의 과장·오서술을 지적하면, 원본으로 재확인해 맞은 지적만 복구하고, 틀린 지적은 기각 근거와 함께 보고한다** — 지적 목록만 넘기고 멈추지 않는다(auditor 자체는 읽기 전용 유지, 복구는 메인 몫. 판정 절차는 auditor·Codex 공통으로 `codex-delegate` 스킬 §3 — auditor 결과를 받을 때도 그 절을 연다).
3. 진행 중·보류·다음 행동이 바뀌었으면 묻지 않고 해당 ws의 `docs/state.md` 갱신(없으면 생성), 보고문에 "state.md 갱신함". 바뀐 게 없으면 쓰지 않고 "state.md 변경 없음(이유)". 자기 `docs/.handoff/` 파일이 있으면 남길 것만 반영한 뒤 지운다(§5). state.md가 6,000자·줄 500자를 넘으면 끝난 섹션을 §5대로 archive로 원문 그대로 옮기고 보고문에 적는다. (Stop hook `state_md_stop_check.sh`가 이번 턴에 커밋하고 state.md를 안 고친 턴을 한 번 막아 확인시킨다. 크기 초과는 막지 않고 PostToolUse `state_md_size_post.py`가 턴당 한 번 알린다)

곁들인 자동화

아래 중 세 도구(subdisplay·usage-indicator·tok_refresh)는 공개 저장소 agent-sidekick-tools에 코드가 있습니다.

  • subdisplay: 태블릿을 보조 화면으로 연결하여 에이전트 상태, 점검 목록, 시스템 리소스 현황을 로컬 문서 기반으로 실시간 공유하는 도구입니다.
  • usage-indicator: 여러 에이전트 CLI의 사용량과 갱신 잔여 시간을 상단 패널에 상시 표시하고 파일로 공유해 중복 조회를 방지하는 모니터링 도구입니다.
  • tok_refresh: 5시간 단위 사용량 제한은 첫 요청 시점에 따라 갱신 시각이 매일 달라집니다. 클라우드 예약 작업이 정해진 시각마다 짧은 요청을 보내 그 시각을 고정하고, 하루 사용량을 업무 시간에 맞춰 나눠 쓰게 하는 장치입니다.
    • 이 예약 작업은 Oracle Cloud의 메모리 1GB 가상 서버에 SSH로 접속해 cron으로 구성·운영하며, 로그 크기 제한을 두었습니다.
    • 예약 실행과 수동 작업이 겹쳐 서버 메모리가 바닥나고 원격 접속까지 끊긴 뒤로는, 중복 실행 차단·swap 추가·실행 시간 제한을 더했습니다.
  • 일일 브리핑: 여러 작업 공간의 변경 이력과 상태를 모아 요약하고 다른 모델로 교차 점검해 보고서를 생성하는 수동 실행 요약 절차입니다(교차 점검은 보조라, 실패한 날에는 점검 없이 생성).
  • 지원현황 점검: 지원 서류 폴더의 위치, 마감일, 상태 표기 불일치를 매일 밤 자동으로 점검해 정리하고 변경 사항이 있을 때만 알림을 주는 스크립트입니다.
  • 사실 보존 검사: 문체를 자연스럽게 다듬는 과정에서 수치, 코드 낱말, 인용구 등 핵심 사실이 왜곡되거나 누락되지 않았는지 전후 차이를 대조하는 검사 도구입니다.

배운 점·한계

협업 체계를 운영하면서 배운 점

  • 계획 먼저이미 잘못 진행된 작업을 되돌려 처음부터 다시 시작하는 비용을 치르기보다, 작업 착수 전에 방향과 범위를 명확히 정의하고 계획을 꼼꼼하게 수립·검증하는 것이 무엇보다 중요
  • 모델 분배최고 성능의 플래그십 모델이라도 모든 과정에 똑같이 쓰기보다, 작업 성격과 단위에 맞추어 모델을 분배하고 연산 강도를 조절하는 유동적인 협업 감각
  • 효과실제로 이러한 장치들을 통해 개발과 문서 작업 전반에서 불필요한 시행착오를 줄이고 진행 시간을 아낌

다만 자동 차단 장치는 위험한 명령의 실행을 막은 것이지, 실제 사고를 막았다는 뜻은 아닙니다.

  • 차단 건수일부는 규칙 검증을 위한 시험이거나 정상 입력을 막았던 오탐을 포함
  • 효율·안전 효과체감에 기반한 것으로, 정밀하게 수치화하여 측정한 것은 아님
  • 운영규칙을 한 번 정한다고 끝나는 것이 아니라, 작업 변화에 맞춰 가드레일과 승인 기준을 지속적으로 관찰하고 다듬어 나가는 과정이 필수
